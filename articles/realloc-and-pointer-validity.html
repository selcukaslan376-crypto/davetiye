What Happens to a Pointer After realloc?

realloc has two main outcomes, and the validity of the old pointer is different in each. Correct code makes that branch explicit.

realloc is often described as “resize this allocation.” That description hides the ownership transition that matters most: on success, the old allocated object is gone and the returned pointer refers to the resulting allocation; on failure for a nonzero request, the old allocation remains. The program must preserve enough information to handle both outcomes.

The realloc contract

The function is declared in <stdlib.h>:

declaration
void *realloc(void *ptr, size_t size);

For an ordinary nonzero request, ptr is either a null pointer or a pointer previously returned by an allocation function and not yet deallocated. Passing a null pointer makes the call behave like an allocation request. Passing a pointer to an automatic object, an interior pointer, or an already freed allocation has undefined behavior.

If a new allocation is produced, the existing bytes are preserved up to the smaller of the old and new sizes. When the allocation grows, the additional bytes have indeterminate values; they are not automatically zero-initialized.

Note

This article is original introductory sample content focused on C99 and C11. It summarizes behavior in practical terms and does not quote or replace the ISO C standard.

After successful reallocation

When realloc succeeds, it returns a pointer to the resulting allocated object. The old allocated object is deallocated. The returned address may look numerically identical to the old address, or the allocation may move; portable code must be correct in either case.

success-model.c
int *old_value = buffer;
int *resized = realloc(buffer, new_size);

if (resized != NULL) {
    /* Do not evaluate old_value or buffer here. */
    buffer = resized;
}

The variable buffer still physically contains bits after the call, but after success its old pointer value no longer provides access to a live allocation. Under the C object-lifetime rules, pointer values referring to an object become indeterminate when that object reaches the end of its lifetime. Do not dereference, compare, subtract, print, or otherwise evaluate the old value after a successful call. Overwrite the owner variable with the returned value.

This is stricter—and safer—than saying “do not use the old pointer only if the block moved.” The program cannot test whether it moved by comparing the result with the now-invalid old pointer. It does not need to know.

Warning

Even when an implementation returns the same numerical address, success ends the old allocated object’s lifetime. Reason from the allocation contract, not from printed addresses.

After failed reallocation

For a nonzero size request, failure is reported with a null pointer. The original allocation is not deallocated, and the original pointer remains the program’s way to access or eventually free it.

failure-branch.c
int *resized = realloc(buffer, new_size);

if (resized == NULL) {
    /* buffer still refers to the original allocation. */
    report_allocation_failure();
} else {
    buffer = resized;
}

This asymmetric result is useful: a failed growth request does not destroy existing data. It also explains why code must not replace the only owner pointer before it knows whether the call succeeded.

The temporary-pointer pattern

Assigning the result directly to the original pointer combines the result variable and the owner variable too early:

wrong.c
buffer = realloc(buffer, new_size);
if (buffer == NULL) {
    /* The original allocation still exists, but its pointer was lost. */
}

On failure, realloc returns null and the assignment overwrites the only saved pointer. The allocation is now unreachable through the program’s intended owner: a memory leak.

Keep the result separate until the branch is known:

resize-array.c
#include <stddef.h>
#include <stdlib.h>

int resize_samples(int **samples, size_t count)
{
    int *resized = realloc(*samples, count * sizeof **samples);

    if (resized == NULL) {
        return 0;
    }

    *samples = resized;
    return 1;
}

This function assumes count is nonzero and that the multiplication has already been shown safe; the next sections address both qualifications. On failure, *samples remains unchanged. On success, the assignment replaces its indeterminate old pointer value without first evaluating that value.

Tip

Name the temporary after the outcome—resized or new_buffer—and update the owner immediately after the null check. This keeps the lifetime transition visible.

Aliases and interior pointers

Updating the main owner pointer does not repair other pointer objects that referred to the old allocation. After successful reallocation, every saved pointer into the old object—including pointers to its elements—is invalid.

stale-alias.c
int *third = &buffer[2];
int *resized = realloc(buffer, new_count * sizeof *buffer);

if (resized != NULL) {
    buffer = resized;
    /* third is invalid; derive it again if index 2 still exists. */
    third = &buffer[2];
}

The safe general approach is to store stable logical information—such as an index—across the call and derive interior pointers again from the returned allocation. The example also requires new_count > 2 before reconstructing third.

Check the size calculation first

realloc receives a byte count. When a program multiplies an element count by an element size, unsigned size_t arithmetic can wrap before the function is called. The allocator then receives a smaller, apparently valid request.

checked-size.c
#include <stdint.h>
#include <stdlib.h>

if (new_count > SIZE_MAX / sizeof *buffer) {
    /* Requested byte count is not representable. */
    return RESIZE_FAILED;
}

size_t bytes = new_count * sizeof *buffer;
int *resized = realloc(buffer, bytes);

Using sizeof *buffer keeps the allocation tied to the pointed-to type and avoids repeating that type in the expression. The overflow check belongs before the multiplication.

Treat zero-size requests cautiously

The C99 and C11 specifications permit implementation-defined behavior when the requested size is zero. The call may return a null pointer, or it may return a value that must not be used to access an object. Later language revisions and implementations add further historical complications.

A null result is therefore not a portable failure signal when the requested size is zero. Code that wants “resize to zero” is clearer when it handles that policy before calling realloc:

explicit-zero-policy.c
if (new_count == 0) {
    free(buffer);
    buffer = NULL;
    capacity = 0;
    return RESIZE_OK;
}

This avoids depending on an implementation’s zero-size convention and leaves the owner in an explicit state. A project targeting a particular C revision and platform should document any different policy.

A compact working model

  1. For a nonzero request, null means failure and the original allocation remains live.
  2. A non-null result means success; the old allocated object is gone.
  3. After success, do not evaluate the old pointer value—even if the returned address appears unchanged.
  4. Use a temporary pointer so failure cannot overwrite the only owner.
  5. Rebuild pointers into the allocation after success; old aliases and interior pointers are invalid.
  6. Check count-times-size overflow before calling realloc.
  7. Handle a desired zero capacity explicitly instead of using a zero-size result as a portable success-or-failure test.
